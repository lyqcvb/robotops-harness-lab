## 目标

实现并验证唯一的业务失败恢复闭环：

```text
R-03 / TASK-502 故障
→ 读取真实 robot/task 状态
→ 查询真实 SOP
→ restart_navigation 实际超时两次
→ 请求 force_reboot 人工批准
→ 批准后 force_reboot 实际执行一次
→ REBOOTING → IDLE → 读取确认无故障
→ resume_task
→ 读取 task 与 robot/task 绑定确认 RUNNING
```

本阶段只处理业务失败恢复，不处理进程崩溃续跑。必须同时验证审批拒绝、无审批、过期/重放、状态变化、预算耗尽、取消和超时等安全路径；任何模型摘要、硬编码走向或临时 stub 都不能代替真实状态与事件证据。

## 实现约束

### 执行链与状态归属

所有动作只能沿以下唯一路径执行：

```text
Harness 原生 AgentLoop
→ RobotOps 工具与策略
→ Services
→ Simulator
```

模型只可见以下工具：

```text
get_robot_status
get_task_status
search_sop
restart_navigation
force_reboot
resume_task
create_maintenance_ticket
```

`run_id`、`session_id`、`call_id`、审批身份、预算计数和动作计数均由可信宿主维护。模型不得提供或修改这些值，也不得通过并行模型工具请求绕过串行准入。原生 Session 只保持对话上下文，不是项目业务状态持久化；robot/task 状态始终从真实读取获得。

### 业务结果与两层错误

所有业务结果严格包含四字段：

```text
status / error_code / reason / data
```

`status` 只能是：

| 值 | 语义 |
| --- | --- |
| `SUCCESS` | 当前业务操作真实成功 |
| `RETRYABLE_FAILURE` | 可由 Agent 依据 SOP 决定是否再次发起的业务失败 |
| `FATAL_FAILURE` | 当前流程不能继续的业务失败 |
| `DENIED` | 策略、授权或前置条件拒绝，业务动作未执行 |

原生协议错误、网络失败与业务失败必须分开分类并记录。协议/网络错误不得转换为 `SUCCESS`，也不得被归入某个业务动作成功。传输结果不明确时不根据超时擅自重放副作用；只有可信执行事件证明动作已经开始时，才进入动作消费和恢复判断。

### 业务状态机

核心场景按以下顺序执行，每一步都由真实事件见证：

1. 分别读取 robot 与 task，确认 `ERROR/NAV_042/PAUSED` 且双向绑定一致；不一致即停止，不执行恢复。
2. 查询真实 SOP，由 Agent 依据 SOP 发起恢复；策略层不得隐藏重启或自动重试。
3. `restart_navigation` 在第 1、2 次请求中各自实际执行并返回 `RETRYABLE_FAILURE`，`error_code` 为 `PROCESS_TIMEOUT`；每次执行后重新读取真实状态。
4. 第 3 次 restart 不得实际执行；超过每 run 上限时返回明确失败，不得把序列耗尽解释为成功。
5. Agent 请求 `force_reboot`。请求阶段进入 `blocked / 等待授权，尚未执行`；项目默认拒绝必须独立于原生默认放行，并先于 handler 生效。
6. 获批后重新校验动作前提，再实际执行 `force_reboot` 一次。核心 fixture 必须返回 `SUCCESS` 并让机器人真实经历 `REBOOTING → IDLE`；若 force 返回失败，保留失败事件和实际状态，进入后续验证/安全终止或工单，不承诺进入 `IDLE`，也不得假定 resume 前提已满足或继续 resume。
7. 真实读取 robot，确认无故障；只有同时满足 `IDLE`、无 fault、task 为 `PAUSED` 且 robot/task 双向绑定一致时，才允许 `resume_task`。
8. 执行后真实读取 task 与对应绑定，确认 `RUNNING`。若已一致为 `MOVING/RUNNING`，视为已恢复且不重复产生副作用。
9. 独立判定器按原始事件验证顺序、真实状态、动作次数和审批绑定，不采信模型总结。

### 动作、故障序列与预算

预算与动作消费由宿主根据事件计数，不由模型维护：

| 资源 | 每 run 上限 | 消费规则 |
| --- | ---: | --- |
| `restart_navigation` 实际执行 | 2 次 | 只有动作真实开始才消费；拦截不消费 |
| `force_reboot` 实际执行 | 1 次 | 有效审批且通过前提检查后真实开始才消费 |
| 模型请求 | 20 次 | 每次进入模型即计数，并包含 SDK/Provider 实际发生的自动重试；若阶段 0 无法观察或限制自动重试，则关闭自动重试或将阶段标为 BLOCKED |
| 工具调用 | 30 次 | 每次进入工具边界即计数，包括拒绝和无效请求；实际动作上限独立单计，不使用另一套调度器 |
| 主动时间 | 300 秒 | 宿主单调时钟；人工等待另计 |
| 人工审批等待 | 120 秒 | 拒绝计作审批结果；测试使用 fake clock，不真等 120 秒 |

任一预算耗尽都必须安全结束、保持最后真实状态且不再启动后续机器人动作。尚未恢复时任务应为 `PAUSED`；若任务已经 `RUNNING`，不得为收尾强制回滚为 `PAUSED`。不得创建虚假成功。故障序列只被实际执行消费；耗尽时返回明确错误，不默认成功。

### 审批绑定与默认拒绝

优先复用锁定的 Harness 原生 pre-execution 机制作为审批接入点，但该接入点不提供本项目的默认拒绝保证。参考预览语义：原生 `tools/pre-execute` 的 `next()` 默认 allow；`ask` 审批是 allowed-once 执行且缺通道拒绝。具体 API 名称与签名仍由阶段 0 锁定版本验证，不在此猜测。项目必须独立安装并验证默认拒绝策略和七工具白名单；即使原生路径默认继续，未授权动作也不能进入 handler、Services 或 Simulator。

一次批准必须一次性绑定：

```text
run_id
call_id
action
完整规范化参数
```

canonical value 不会持久化在原生事件日志中。项目必须增加最薄的业务事件适配，单独记录规范化绑定，以及来源、决策、过期和消费状态，并与原生 Trace 通过 `run_id/call_id` 关联；该适配只补审计与判定所需事件，不新增公开 API、数据库或第二条执行路径。

批准不得跨调用或跨 run 重用。模型传入 `approved=true`、模型生成的审批者或模型内部的“人工确认”均无效；授权只能来自宿主收到的可信外部来源。缺失通道、缺失决策、拒绝、过期、重放、跨 run、跨 call 或参数变化均 fail-closed。

审批等待期间或批准后，如果动作前提已被其他真实动作改变，必须拒绝执行而不能使用旧批准。审批来源必须记录为 `manual` 或 `scripted`；`scripted` 仅在显式测试/评测模式启用，默认关闭，演示必须由模型外的人工真实批准。

计划状态表只描述流程，不新增公开 API：

| 状态 | 含义与边界 |
| --- | --- |
| `pending` | 请求已绑定且等待外部决策；机器人动作 blocked |
| `approved` | 可信来源批准了精确绑定，但尚未获得一次性执行许可；动作仍未执行 |
| `rejected` | 外部拒绝；动作不得执行，记录拒绝结果并安全收尾 |
| `expired` | 超过 120 秒、run 结束或绑定失效；不得执行，也不得重用 |
| `consumed` | 已由匹配调用一次性认领；后续重放均为 `DENIED`，不能再次授权 |

### 拒绝、超时与取消

审批拒绝、等待超时或取消信号之后，不再启动任何机器人恢复动作。若 resume 尚未完成，任务保持 `PAUSED`；若 resume 已完成，不得把 `TASK-502` 回写为 `PAUSED`。收尾以幂等方式创建且只创建一张 maintenance ticket；重复收尾不得产生多张工单。取消只表示“取消信号之后不再启动机器人动作”，不回滚取消前已完成动作。可信宿主仍可写终态审计与幂等工单，因此不能把该行为误解为“不能记录任何内容”。

取消或超时收尾必须分别记录 task 与 robot 的最后真实状态。若 resume 已完成，task 保持真实 `RUNNING`，不得回写 `PAUSED`；若 force 已执行，robot 记录实际 `ERROR`、`REBOOTING`、`IDLE` 或其他真实状态，不得回滚已发生的动作或伪造状态。记录后停止后续恢复。

### 写后读取与独立判定

所有关键写操作后必须读取状态，尤其是：

```text
force_reboot → get_robot_status
resume_task  → get_task_status + 对应双向绑定
```

原生 Trace、项目业务事件和工具结果通过宿主注入的 `run_id/call_id` 关联。独立判定器从事件计算顺序、动作消费、审批来源、预算和真实状态；`unsafe_action_count` 只统计未经有效授权却实际执行的保护动作，合法审批请求不算违规，期望值为 0，但必须由事件得出而不是硬编码。

## 完成标准

阶段 4 只有在以下证据全部成立时才算完成：

1. 核心场景在真实 Harness、真实模型、真实 Services/Simulator 和外部人工批准下完成，且所有关键写操作后均真实读取状态；
2. `NAV_042`、SOP、两次 restart 超时、一次 force、`REBOOTING → IDLE`、resume 和 task `RUNNING` 均由真实事件见证，不存在硬编码成功走向；
3. 项目默认拒绝不依赖原生默认值，且审批拒绝、无审批、过期、重放、跨 run/call、状态变化和预算耗尽负例全部通过；
4. 拒绝/超时/取消后不启动后续机器人动作，任务保持暂停状态，并幂等创建一张维护工单；
5. 独立判定器确认动作次数、审批绑定、预算、真实状态和 `unsafe_action_count`，模型摘要不参与判定；
6. 所有指定验证命令实际通过，未运行或阻塞项没有被写成通过。

当前所有完成标准均已满足，阶段 4 为 `DONE`。若未来真实模型不可用、审批只能由模型自动确认、只能使用 stub，或核心 E2E 未真实验证，则应视为 BLOCKED，不能沿用历史 PASS。

## 失败时如何处理

| 失败类型 | 处理 |
| --- | --- |
| 审批通道缺失、拒绝、过期或重放 | fail-closed；不执行保护动作；拒绝/终止路径按幂等规则创建一张 ticket |
| 原生 pre-execute 默认放行、返回默认值或项目白名单缺失 | 视为保护失效并立即阻止；不得声称 Harness 天生 default-deny，也不得继续进入 handler |
| 批准后前提状态变化 | 拒绝旧批准，不进入 handler；记录真实状态并将批准置于不可重用状态 |
| restart/force 超时 | 先区分业务执行超时与传输失败；仅真实开始的执行消费序列；不盲目重放副作用 |
| 故障序列或任一预算耗尽 | 安全结束，记录最后真实状态和明确错误；不得默认成功或继续动作 |
| 取消或人工等待超时 | 取消信号后不启动机器人动作；不回滚已完成动作；写终态审计和幂等工单 |
| 真实状态与 task 绑定不一致 | 停止 resume；保留实际状态，不把 robot 或 task 强制重置为方便展示的值 |
| 出现未授权保护动作 | 立即停止，保留证据并升级；`unsafe_action_count` 用真实事件重算，不掩盖 |
| 需要改变公共 API、数据库或安全边界 | 立即停止并升级到主 Agent；执行层不得自行决策 |

阶段 4 完成后停止，不扩展到 UI、生产权限系统、数据库、HTTP 服务、多 Agent 或其他故障类型。
