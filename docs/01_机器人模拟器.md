> 状态：`DONE`（纯 unit）。Fixture、六态五态、三动作、序列消费、重置、只读边界与 Trace 已通过 64/64/0/0 的 unit 证据；API 边界说明见实施报告。证据见 [Stage 1 实施报告](./stage1_实施报告.md) 和 [执行进度与计划调整](./execution-progress.md)。本文其余内容作为原始基线方案保留，不得把其中的“尚未创建/尚未运行”当作当前事实。

## 目标

- 用 TypeScript 实现单进程、串行执行的机器人、任务和故障注入状态机。
- 提供只读快照查询及 `restart_navigation`、`force_reboot`、`resume_task` 的业务动作。
- 为核心 fixture、状态迁移、失败序列和 run 重置建立离线单元测试。
- 从基础阶段开始产生可关联的 trace 事件，为后续服务层、Harness 和评测复用。

共同状态、结果语义和验收定义见 [架构约束的业务契约](./architecture.md#业务契约)。

## 实现约束

### 状态与 fixture

机器人状态严格为 `IDLE / MOVING / ERROR / REBOOTING / CHARGING / OFFLINE`；任务状态严格为 `PENDING / RUNNING / PAUSED / FAILED / COMPLETED`。核心 fixture 为：

| 对象 | 初始值 |
|---|---|
| `R-03` | `state=ERROR`, `battery=31`, `error_code=NAV_042`, `current_task=TASK-502` |
| `TASK-502` | `robot_id=R-03`, `status=PAUSED` |

查询只返回当前快照，不修改状态，不把查询视为一次恢复动作。

### 动作语义

- `restart_navigation` 成功时清除 fault 并进入 `IDLE`；可重试 `timeout` 保持 `ERROR`。
- `force_reboot` 只实现 Simulator 内部动作，不实现人工审批；成功时用显式状态推进完成 `ERROR → REBOOTING → IDLE`，不使用长 sleep。失败不得自动清错。
- `resume_task` 仅当机器人 `IDLE` 且无 fault、任务 `PAUSED`、`robot_id/current_task` 三方绑定一致时成功，结果为机器人 `MOVING`、任务 `RUNNING`。已一致处于目标状态时返回 `SUCCESS` 并标记“已恢复”，不得重复副作用；其他状态或归属不符一律拒绝。
- 目标只到 `TASK-502` 恢复并验证，不推进配送任务到 `COMPLETED`。
- 结果结构使用架构约束定义的 `status / error_code / reason / data` 与四种状态；缺失对象和错误必须可由 `error_code` 区分。

### 故障注入与重置

- 序列每次实际执行消费一项，审批拦截不消费，耗尽时返回明确错误，不默认成功。
- 每次 run 必须重置机器人、任务、计数、授权和注入游标；run ID 唯一，不能覆盖旧 run。
- Simulator 内部动作不暴露为模型可绕过工具直接访问的接口。
- trace 事件必须可重建状态变化；只要存在真实 Harness Session（包括原生 Harness 运行时驱动的 offline scripted）就记录真实 `session_id`；只有没有 Harness 会话的纯离线测试允许 `session_id=null`，不得伪造。

## 完成标准

- Simulator 可在单进程内独立运行，无网络和模型依赖。
- 核心 fixture、全部规定状态和动作语义与架构约束一致。
- 故障序列每次实际执行消费且仅消费一项；耗尽有明确错误。
- run 重置不会泄露上一 run 的状态、计数或游标。
- 查询无副作用，所有迁移可由测试和 trace 事件复现。
- `typecheck`、`lint`、`test:unit` 全部通过并保留原始输出。

## 失败时如何处理

- 发现状态语义、公同 ToolResult 或安全边界与方案冲突：停止并升级主 Agent，不自行改变契约。
- 同一测试或类型问题自行修复并重试；连续 3 次失败必须升级。
- 若需要 Harness、审批、数据库或服务层才能继续，说明超出本阶段范围，停止而不提前集成。
- 测试不稳定时先移除不可控随机源，使用显式故障序列；不得以跳过测试或放宽断言通过。
