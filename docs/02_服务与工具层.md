## 实现约束

### Service 边界

- `get_robot_status(robot_id)` 与 `get_task_status(task_id)` 只读返回 Simulator 快照，不把查询记作恢复动作。
- `restart_navigation`、`force_reboot`、`resume_task` 由 Service 代理 Simulator，但不得绕过 Tool/Policy 边界暴露内部对象。
- `search_sop` 只查询静态 SOP；`NAV_042` 是核心 fixture，未匹配时返回明确缺失 error code，不抛裸异常或猜测动作。
- 工单必须按 `run_id + robot_id + reason` 去重；重复请求返回同一幂等结果，不产生第二张工单。
- 工具不得直接修改 Simulator 私有状态，状态变化只能由已定义的 Simulator 动作产生。

### ToolResult 与身份

- 所有工具统一返回 `status / error_code / reason / data`；`status` 仅允许 `SUCCESS / RETRYABLE_FAILURE / FATAL_FAILURE / DENIED`。
- 缺失机器人、任务或 SOP 通过不同 error code 表达。原生协议、运行时或传输异常单独分类记录，不能伪装成业务成功。
- `ExecutionContext` 由宿主注入，不能作为 LLM 工具参数；不得接受模型提供的身份、预算或 `approved=true` 授权。
- `force_reboot` 是保护动作。任何面向模型的暴露路径必须先经过 Policy；项目 default-deny 在审批编排接入前直接返回 `DENIED`。官方文档所述 `next()` 默认 `allow`，因此不能把安全依赖留给 Harness 默认值。
- 本阶段只安装 Policy 缝和 default-deny 边界；审批绑定、一次性消费及审批来源记录在 Stage 4 实现并验证。
- 策略层只限制调用，不暗中重试。业务重试由 Agent 显式发起；传输错误与业务失败独立记录。

### Trace 与幂等

- trace 至少记录 `run_id`、事件序号、工具名、调用关联、请求与实际执行、动作状态变化和幂等结果。
- 每次 run 的数据相互隔离；`run_id` 唯一且不可覆盖，工单去重范围不能跨 run 泄露。
- canonical value 不写入原生 durable 事件，因此项目必须保存自己的事件记录；只要存在真实 Harness Session（包括原生 Harness 运行时驱动的 offline scripted）就记录真实 `session_id`；只有没有 Harness 会话的纯离线测试允许 `session_id=null`，不得伪造。
- 测试不得依赖真实模型、网络、随机数或真实人工审批。

## 失败时如何处理

- 需要改变工具签名、公同类型、身份边界或安全策略时：停止并升级主 Agent，不自行扩大 API 或修改契约。
- 阶段 1 的行为与方案冲突时：停止，保留最小复现并升级；不得在 Service 层偷偷补偿 Simulator 语义。
- 测试失败先在本阶段范围内修复；同一问题连续 3 次失败必须升级。
- 若需要 Harness、真实模型或人工审批才能继续，说明超出 Stage 2 范围，停止而不提前集成。
- 出现模型可绕过工具、直接触达 Simulator 或 default-deny 失效时，立即停止并按安全阻塞处理。
