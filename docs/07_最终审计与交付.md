## 目标

在不增加功能的前提下，对已经完成的实现执行功能、安全、真实性、secret、复现和交付审计，记录每项命令的 `PASS / FAIL / SKIPPED / NOT_TESTED` 与阻塞，并按硬 gate 决定是否可交付。

1. 运行完整计划测试接口，覆盖 typecheck、lint、unit、integration、live E2E 与 eval。
2. 核对 5 个场景的真实运行、完整恢复 arm 的核心批次、全部 run 的安全零违规与独立人工审批演示。
3. 核验结果可重算、失败保留、README 真实且新人可从干净环境复现。
4. 发现问题时只做已明确的小范围修复；不得最后阶段增加功能或降低安全要求。
5. 任何硬 gate 未通过都报告失败或 `BLOCKED`，不为了宣布完成而掩盖问题。

### 审计原则

`SKIPPED` 和 `NOT_TESTED` 都不是完成证据。真实 E2E 缺 key 必须为 FAIL 或 `BLOCKED`，不能显示为绿色 SKIP；首日真实模型、依赖或审批 gate 未通过时只能标 `BLOCKED`，不能把离线部分称为 MVP 交付。

## 实现约束

### 完整验证与状态语义

完整审计覆盖统一计划接口：`npm run typecheck`、`npm run lint`、`npm run test:unit`、`npm run test:integration`、`npm run test:e2e`、`npm run eval`。其中真实 live 路径由 `test:e2e` 与 live `eval` 模式提供；不额外发明未在架构约束定义的脚本。

每个审计项必须记录命令原文、输入前置、环境、日期、退出码、原始输出位置和产物，并按下表解释状态：

| 状态 | 含义 |
| --- | --- |
| `PASS` | 已实际执行，结果满足既定断言并有证据 |
| `FAIL` | 已实际执行，但断言、安全性或真实性不满足 |
| `SKIPPED` | 有意未执行；不计为通过，必须写原因和影响 |
| `NOT_TESTED` | 尚无足够证据或未建立可执行验证；不计为通过 |
| `BLOCKED` | 外部依赖、凭据、版本或人工 gate 阻止，需要用户或主 Agent 处理 |

测试、类型、lint、失败或超时必须先按既有方案修复并重跑。同一问题连续 3 次修复失败，或需要新架构、公共 API、数据库、安全边界决策时，立即升级主 Agent。

### 审计范围

#### 功能与安全

- 逐项核对七工具、状态机、恢复、审批、工单、Trace 和指标的真实行为。
- 核对每 run 预算：20 次模型请求包含 SDK/Provider 自动重试；30 次工具请求包含拒绝和无效请求，并与 `restart_navigation`、`force_reboot` 的实际动作次数分开统计。
- 保护动作始终默认拒绝，任何成功执行都必须有绑定 run、具体调用与参数的一次性有效批准。
- 审批拒绝、超时或取消后不再启动机器人动作；取消不回滚已成功动作，可信宿主只做终态审计和幂等工单收尾。
- 从策略记录与实际动作事实交叉核对 `unsafe_action_count`，不能 hardcode 或只信模型。
- 任何一次无有效批准的保护动作执行都使交付失败，不能用平均值掩盖。
- 不得将官方 `SAFETY.md` 描述为可靠沙箱或生产级隔离。

#### 真实性与结果

- README 陈述分类为 `MEASURED / IMPLEMENTED / DOCUMENTED / INFERRED / PLANNED`，每项必须有代码、命令输出或结果文件来源。
- 找不到证据的成功率、延迟、成本、提升幅度或能力声明必须删除、降级或标未验证。
- 30 次自动实验与至少 1 次真实人工审批演示分开报告；脚本 approval 不称为 human。
- 每个 run 结果以 `run_id` 隔离，manifest、Trace、终态、失败样本和 summary 可追溯。
- 指标必须从原始业务事实独立重算；token/cost 缺失使用 `NOT_MEASURED`，不写 `0`。
- 重测使用新 `batch_id`，旧数据与失败样本均保留，不静默剔除。

#### Secret 与泄漏

- 审计 API Key、Token、密码、`.env`、认证头、内部地址和凭据是否出现在工作区、日志、Trace、README 或素材中。
- 处理过程不得读取凭据，也不修改 `.gitignore`；未来发现暴露时，仅删除工作区文件不算解决。
- 暴露 secret 必须执行撤销或轮换、清理所有可发现泄漏副本并保留不含 secret 的处置记录；处置细节交给主 Agent/用户确认。
- 证据记录不得包含 secret 原文，只能记录泄密路径类别、处置状态和验证结果。

#### README 与干净环境

- 按 README 从相对干净状态完成安装、配置、启动、最小真实路径和测试，记录环境、命令、输出与阻塞。
- 只做低风险清理，不删除证据、不隐藏失败、不在最后阶段大规模重构。
- 无真实机器人、无 3D 物理仿真、无生产环境、Simulator 边界、小样本限制和未验证项必须可见。
- 一个新人应能依据 README 运行；如果必须依赖未记录的内部知识，复现审计失败。

### 交付硬 gate

以下全部满足才允许宣布 MVP 交付：

1. 5 个场景都有真实模型运行证据。
2. 完整恢复 arm 的核心最终批次达到 `3/3` 通过；fail-fast 不要求任务成功，但必须符合各自场景预期。
3. 所有验收 run 的 `unsafe_action_count=0`。
4. 至少 1 次真实模型人工审批 Demo，来源与绑定信息可审计。
5. 所有结果可由保留的原始事件重算。
6. 失败、超时、取消、环境错误和基础设施失败均保留且汇总分母正确。
7. 新人可按 README 完成安装、运行与最小演示。
8. Harness 原生、项目自实现、Mock 与未验证边界清晰。
9. 5 场景 × 3 重复 × 2 配置的 30 次真实自动实验和独立人工演示没有混淆。

## 失败时如何处理

- 若未来阶段 0 的真实模型、依赖或审批硬 gate 未通过，则整体应标记 `BLOCKED`，不得把离线部分称为 MVP 交付；历史 PASS 不自动覆盖新失败。
- 真实 E2E 缺 key、依赖不可用或锁定版本冲突：记录完整错误，标记 FAIL/BLOCKED 并升级；不使用绿色 SKIP、假模型或未验证替代路径。
- 任一验收 run 的 `unsafe_action_count 0`：立即停止交付并升级安全处理；整个验收失败，不能平均或删除记录。
- 指标不可重算、Trace 断链、结果覆盖、失败样本丢失或 denominator 不一致：交付失败，保留证据并修复后重新执行受影响批次。
- 测试、类型或 lint 失败：在既有方案内修复并重跑；连续 3 次失败或需要新设计决策时升级主 Agent。
- 发现 secret：停止发布，按主 Agent/用户确认的流程撤销、轮换和清理，记录泄漏范围与处置结果；仅删除文件不算完成，处理过程不得读取凭据。
- clean-room 复现失败：修正已明确文档或配置错误并重试；若问题暴露架构或环境缺口，标记 BLOCKED，不靠未记录步骤补丁。
- 需要新增功能、改变公共 API、数据模型、并发模型或安全边界：停止实现并升级主 Agent，阶段 7 不做新功能。
- 完成最终报告后停止，不继续增加 Feature。
