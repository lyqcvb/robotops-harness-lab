## 实现约束

- 安装事实以本地锁版本为准，接口依据已安装 README/d.ts；静态依赖不等于运行能力。当前原生 Loop、工具、审批与 Session 的通过结论有实际运行证据。
- Cordis 4 使用 `await ctx.plugin(...)` 与 `ctx.fiber.dispose()`，不存在 `ctx.start/stop`；`ctx.agents.create(...)` 返回 `agent/dispose`，以 `agent.followup(...)`、`agent.whenIdle()` 驱动。
- Tools 使用 `defineTool`、`tools.guard()`、`'tools/pre-execute'`；审批使用 `request(req)`，Session 订阅 `session/event`。官方 `next()` 默认 `allow`，项目 default-deny 不是 Harness 整体默认。
- 七工具与架构约束白名单一致，参数不接受 `approved=true`，身份由宿主注入；保护动作需绑定调用和参数的一次性授权。scripted 审批已验证，真人审批仍由 Stage 4/6 完成。
- Session flush 后通过官方 `sessionPersistence` read 路径（`open(sessionId, 'read')` → `handle.read(0)`）逐事件核对 snapshot 与序号，不以 JSONL 文件存在替代验证。
- LIVE 中成功 canonical JSON 是工具 render 后的原生 `tool/result` 文本，不等于原生 durable 事件保存了独立的 typed canonical value；业务重算仍依赖项目自建事件。
- 原生 JSONL 留在 `.stage0` 隔离根、不恢复；脱敏 evidence 每 run 不覆盖，报告只能读取。offline 与 live 分栏，失败与缺凭据安全负例均保留。
- npm 网络按用户环境配置；probe 入口已带 `--use-env-proxy`。不改镜像或全局设置，不宣称生产级隔离或安全审计通过。

## 失败时如何处理

- 后续复现出现 registry/代理错误时保留错误，检查用户自身代理配置；不以未经验证的镜像掩盖问题。
- 缺 key 或真实模型请求失败时标记实际 `BLOCKED`/失败并保留独立 run，不覆盖最终验收历史，不用 scripted 请求冒充真实 API。
- 版本、接口与既定方案冲突时停止实现并升级主 Agent，不自行改变公共 API、安全边界或架构。
- 审批、白名单、事件核对失败时当前复现不得通过；同一问题连续 3 次修复失败必须升级。
- 若出现业务副作用、旁路访问或重复授权执行，立即停止并保留证据升级。已有最终 `PASS` 不能作为新运行失败的豁免。
- 进入后续阶段需要单独执行并满足各自门槛；文档检查只验证格式与引用，不能代替业务验收或真实人工演示。
